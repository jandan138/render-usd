Camera Distance Bug：一条 np.clip 引发的血案

2026-03-08，批量渲染结果突然出现极端特写。调查发现，罪魁祸首是一条出于好意的 np.clip(distance, 0.1, 100.0)。这是一个经典的「防御性编程反噬」案例。

现象

  • 旧渲染（2026-01-19）：物体占画面 ~60-65%，构图正常
  • 新渲染（2026-03-05）：物体塞满整个画面，甚至超出边界
  • 影响范围：所有大尺寸家具（床、沙发、衣柜）

排查过程

最初的怀疑对象是同时期引入的两项改动：

  • Commit A：在渲染循环中加入 world.reset()
  • Commit B：引入 HDRI + backgroundZeroAlpha + alpha compositing

通过环境变量开关做 A/B 测试：

测试跳过 world.reset跳过 alpha 合成结果
Test A否否❌ 特写
Test B是否❌ 仍然特写
Test C否是❌ 仍然特写

结论：两个 suspected change 都不是根因。

真相：np.clip 的 upper bound

加入 debug logging 后，发现问题资产的 distance 被 clamp 了：

debug log
# bed asset: 0a85b986de35ccfdec7c686d791fd747
bbox_min = [-97.83, -111.92, -45.00]
bbox_max = [97.83, 111.92, 45.00]
diagonal = 310.63           # 正确距离
distance = 100.0            # 被 np.clip 截断！只剩 ~32%

np.clip(distance, 0.1, 100.0) 的 upper bound 100.0 假设了「米级坐标」。但 GRScenes 资产使用厘米级坐标，一张床的对角线轻松达到 300-500cm。upper bound 把相机距离截断到原本的 1/3，自然变成极端特写。

修复与教训

fix
# Before (bug)
distance = np.clip(distance, 0.1, 100.0)

# After (fix)
distance = max(distance, 0.1)   # 只防除零，不限制上限
关键教训：
  1. 「防御性编程」如果基于错误假设，会比不防御更危险。np.clip 的 upper bound 静默截断了合法值，没有任何报错。
  2. 添加任何数值限制前，必须了解数据的实际分布和单位。
  3. Debug logging 是定位 silent truncation 的唯一手段。
